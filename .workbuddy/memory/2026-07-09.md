## AI 语音对话 Agent 系统设计方案（毕设拓展）

- 阅读了 `internal/service/free_talk.go`（运行的 VAD+ASR+LLM+TTS 多 goroutine 流式管道）与 `internal/service/conversation_memory.go`（短期记忆 + 摘要重建）。
- 关键发现：`domain.LLMProvider` 与 `internal/infrastructure/llm/qwen/adapter.go` 当前**仅支持普通对话，无 function calling / 工具调用接口**。QwenAdapter 用的是 OpenAI Responses API，SDK 原生支持 Tools，因此加工具调用只需扩接口 + 适配器实现。
- 现状四要素缺口：LLM=应答器(无决策)；Planning=无(仅 silenceWatcher 静默引导)；Tool use=无(但系统已有 EvaluationProvider/PronunciationService/EvaluateService/report_service 等能力未对 LLM 开放)；Memory=仅短期不持久，buildUserProfile 是桩。
- 产出：`docs/AI语音对话Agent系统设计方案.md`，核心思路——不动语音管道，只在 ASR 与 TTS 之间插入 Agent 编排层(Agent Loop)，补齐 Planning/Tool use/Memory；LLM 加工具调用接口；工具分同步(get_user_profile/list_units/get_report)与异步交互(start_practice/assess_pronunciation 需等用户音频)；三层记忆(短期/长期语义/情景)；语音特处理(边想边说、控制权让渡、silenceWatcher 升级为基于 GoalState 主动推进)。

## P1 实现：同步工具 + ReAct 多步循环（已落地，go build / go test 通过）

- `domain/llm.go`：`Message` 扩展 `ToolCalls []ToolCall`（assistant 发起）与 `ToolCallID string`（tool 角色回灌，用于关联 function_call_output）。
- `qwen/adapter.go`：`ChatWithToolsStream` 的 messages→items 转换现支持三类——assistant+ToolCalls → `OfFunctionCall`；tool 角色 → `OfFunctionCallOutput`（`Output.OfString` 传工具结果文本）；默认 → `OfMessage`。注意 `constant.FunctionCall` / `constant.FunctionCallOutput` 是**具名 string 类型**，必须写成 `constant.FunctionCall("function_call")` / `constant.FunctionCallOutput("function_call_output")`，不能当值用。
- `agent/agent.go`：`RunTurn` 改为返回由 `reactLoopDecoder` 驱动的流。该 decoder 在流内部跑多步循环——每步调 `llm.ChatWithToolsStream`；转发文本增量给 TTS（边想边说）；终态事件若带 ToolCalls 则 `executeStep`（追加 assistant 工具调用消息 + 逐个执行并回填 tool 结果消息），`step++` 继续；无 ToolCalls 则发干净 `IsDone` 收尾；`step>=maxSteps` 时最后一步 `Tools=nil` 强制纯文本收尾（防无限循环）。对 `free_talk.go` 完全透明。
- `service/agent_tools.go`（新增）：实现 3 个同步工具 `Tool`——`list_pronunciation_units`(调 `PronunciationService.GetUnitList`)、`get_user_profile`(序列化 `UserProfile`，始终注册)、`get_learning_report`(调 `ReportService.ReportMVP`，裁剪 JSON 输出)。`Session.registerAgentTools` 按"依赖非空"注册：service 为 nil 时跳过该工具，注册表空则退化纯对话（与 P0 一致，nil-safe 不 panic）。
- `service/free_talk.go`：`Session` 加 `pronunciationService`/`reportService` 字段；`NewSession` 增加尾参 `pronService, reportService`；`Run()` 建注册表→`registerAgentTools`→`NewAgent`。`llmGoroutine` 消费 `RunTurn` 不变（读 `ev.Text`）。
- `service/chat_service.go` + `app/app.go`：`chatServiceImpl` 接 `pronunciationService`/`reportService`；`initServices()` 把 `ReportService` 创建提前到 `ChatService` 之前，新建 `PronunciationService`，并把二者注入 `NewChatService` 尾参。
- **关键 runtime bug 修复（务必记住）**：原 `agentStreamDecoder` 仅在"有工具调用"时才发 `IsDone` 终态事件；纯文本回复流结束直接 `return false` 不产 `IsDone`。但 P1 的 `reactLoopDecoder` 靠 `IsDone` 判定单步结束——否则**纯文本轮会无限重试调 LLM**。已修复为：无论有无工具调用，流末尾都发 `IsDone:true` 事件。并新增 `adapter_test.go`（`TestAgentStreamDecoderPlainTextEmitsDone` / `TestAgentStreamDecoderToolCallEmitsDoneWithCalls`）做回归守护。
- 测试：`internal/agent` 单测扩到 5 个（透传、工具 specs 透传、ReAct 多步循环、maxSteps 兜底、Registry）；均绿。`go build ./...` 全通过。`go vet ./...` 仍仅报那个预先存在的 `tts/aliyun/client_test.go:137 unreachable code`（不在本次改动范围，未动）。
- 注：`TestQwenAdapterChatStream` 是预先存在的真实 API 集成测试，受网络/限流影响偶发 flaky，单独跑通过，与 P1 改动无关。
